Bug Corrigido — NETBIRD_NOT_READY
Campo JSON errado na leitura do status do NetBird
O k3ctx perguntava pro NetBird: "você está conectado?" mas lia a resposta no campo errado.
Como funciona o fluxo de verificação
1. CLI executa
netbird status --json
→
2. NetBird retorna
"daemonStatus": "Connected"
→
3. k3ctx lia campo
"status" (vazio!)
→
4. Resultado
NETBIRD_NOT_READY
O que o JSON real do NetBird retorna
{ "daemonStatus": "Connected", ← campo real "management": { "connected": true ... }, "peers": { "total": 29, "connected": 19 ... } }
// netbird/netbird.go type statusOutput struct { Status string `json:"status"` Peers peersSection `json:"peers"` } // "status" não existe no JSON // → Status sempre vazio "" // → tratado como "Unknown"
// netbird/netbird.go type statusOutput struct { Status string `json:"daemonStatus"` Peers peersSection `json:"peers"` } // lê o campo correto // → Status = "Connected" // → preflight passa ✓
Por que o hosts funcionava mas o connect falhava?
O comando k3ctx hosts usa o NetBird apenas para listar peers (lê peers.details[]). O comando k3ctx connect faz uma verificação de preflight lendo daemonStatus antes de qualquer coisa — e era aí que travava.
Bug Encontrado — AMBIGUOUS_MATCH no filtro posicional
Argumento posicional de host não filtra corretamente
Passar um hostname específico retorna todos os peers conectados em vez de filtrar pelo nome.
Comportamento observado
$ k3ctx connect \ systemframe prd-us-00002 EXIT 3 AMBIGUOUS_MATCH Múltiplos hosts encontrados: systemframe-sf-tst-us-00004 systemframe-sf-prd-us-00001 systemframe-sf-prd-us-00008 ... +7 mais ⚠ Nenhum desses é prd-us-00002!
$ k3ctx connect \ --context \ systemframe-sf-prd-us-00002 EXIT 0 { "ok": true, "addr": "sf-prd-us-00002 .systemframe.vpn", "dry_run": true }
O que provavelmente está acontecendo
Input
prd-us-00002
→
Filtro interno (bug)
ignora o substring, lista tudo
→
Resultado
10 hosts sem relação
→
Erro
AMBIGUOUS_MATCH
Workaround enquanto o bug não é corrigido:
Use sempre --context systemframe-sf-<id> em vez dos argumentos posicionais.
O --context resolve direto pelo nome do context, sem passar pelo filtro de substring.

NetBird diz "Connected" mas ICMP/SSH não chegam nos hosts
O k3ctx está correto — o problema é de rede/ACL fora do código.

Evidências coletadas
# NetBird reporta "Connected" para ambos daemonStatus: "Connected" sf-prd-us-00002 → status: Connected, lastHandshake: 1 min atrás sf-tst-sp-00003 → status: Connected, lastHandshake: 1 min atrás # Mas ICMP não chega $ ping 100.64.214.50 From 100.64.0.1: Destination Host Unreachable ← gateway NetBird rejeita # E SSH também não $ ssh sf-prd-us-00002.systemframe.vpn No route to host
Causas prováveis
1
ACL do NetBird — a policy de acesso entre omarchy e esses dois peers pode não permitir tráfego. Verificar no painel NetBird → Access Control → Policies.
2
Firewall nos hosts remotos — sf-prd-us-00002 é EC2 e pode ter Security Group bloqueando porta 22 ou ICMP da subnet 100.64.0.0/16.
3
WireGuard handshake ≠ rota ativa — o NetBird pode registrar handshake mas a rota específica para esses IPs não estar propagada neste peer.
4
Peers offline ou sem daemon — os hosts podem estar ligados no NetBird mas com o serviço k3s ou SSH parado.
Como investigar:
No painel NetBird → Peers → verificar se sf-prd-us-00002 e sf-tst-sp-00003 têm ACL de acesso com omarchy. Se EC2, verificar Security Groups na AWS permitindo CIDR 100.64.0.0/16.
